## 未发布 — 2026-11-26（召回链路补链，`VERSION` 仍 0.17.0）

**一句话**：修正回流此前只在状态机里生效，线性引擎、JSON 输出和网页都看不见它；
这次把链路补齐，并让"这次召回到了什么、有多相关"可查。**检索算法没动**。

### 改了什么

- **线性引擎也召回**：`--linear` 与状态机走同一套 `select_lessons`，SQL 与 pandas
  两条路线都把命中的已确认口径拼进 Prompt；递归重试沿用同一份，不重复算分。
- **召回结果可见**：`-f json` 与 MCP 返回值新增 `lessons`
  （`used` / `top_score` / `signature`）；网页在结果上方显示
  "参考已确认口径 L001（相关度 0.85）"。没有召回时不显示。
- **质量可观测**：新增 `recall_stats()`，`top_score` 是命中的最高相关度，
  `signature` 表示是不是靠库外口径词（如"大单"）命中。两引擎的日志汇总行与
  阶段事件都记这两个标量；口径词原文是数据，不进日志。

### 没改什么

- `select_lessons` 的签名和相关度判据没动，门槛仍是 0.42；缓存、结构审查、
  时间锚点、MCP 鉴权全部保持原样。**这不是检索式问题库，也不是向量召回**。

### 验证

  payload 字段、日志白名单）；评测 53/53、88,846 输入 tokens（模型波动）。
- 冒烟：教一条"华南的销售额"后，线性引擎 `lessons_used=['L001']`、

## 0.17.0 — 2026-11-26

**一句话**：MCP 除了 stdio 还能走 streamable-http，跨机器调用不再难；但默认只监听本机，
跨机器必须带令牌、校验 Host，并且默认不暴露会写盘的工具。

### 一、用户能感受到的变化

- `python -m app.cli serve --transport streamable-http` 启动 HTTP 端点，默认
  `http://127.0.0.1:8000/mcp`；原来的 `serve` 仍是 stdio，行为零变化。
- 跨机器监听（`--host 0.0.0.0` 或局域网 IP）**必须先设 `AGENT_MCP_TOKEN`**
  （至少 16 字符），否则直接启动失败并给出可执行提示。客户端用
  `Authorization: Bearer <token>` 调用。
- 每次请求先验 `Host` 白名单（挡 DNS rebinding）再验令牌；失败返回结构化 JSON
  401/403，不回显令牌、不给 traceback。
- 非本机 HTTP 默认**只读**：工具列表里没有 `generate_catalog`，`ask(chart=true)` 明确拒绝；
  只有显式 `--allow-write` 才放开写盘。本机 stdio/HTTP 不受影响。

### 二、新增参数与环境变量

| CLI | 环境变量 | 默认 | 说明 |
| --- | --- | --- | --- |
| `--transport {stdio,streamable-http}` | — | `stdio` | 传输方式 |
| `--host` | `AGENT_MCP_HOST` | `127.0.0.1` | 非本机需令牌 |
| `--port` | `AGENT_MCP_PORT` | `8000` | — |
| `--path` | `AGENT_MCP_PATH` | `/mcp` | 端点路径 |
| `--token` | `AGENT_MCP_TOKEN` | 空 | 建议用环境变量，避免进程列表泄露 |
| `--allowed-host` | `AGENT_MCP_ALLOWED_HOSTS` | 空 | 可重复 / 逗号分隔 |
| `--allow-write` | — | 关 | 非本机 HTTP 放开写盘工具 |

### 三、实现上的三个刻意选择

- **只传目标版本认识的参数**：mcp 1.x 把 HTTP 配置放构造函数、2.x 放 `run()` /
  `streamable_http_app()`，`_supported_kwargs()` 按签名过滤，不写两份 server 实现。
- **鉴权包在 ASGI 最外层**：不依赖换过位置的 SDK `transport_security`，两个版本行为一致，
  也不会漏掉 `/mcp` 之外的路径；`hmac.compare_digest` 比较令牌。
- **uvicorn 延迟导入**：MCP 仍是可选项，没装 mcp / uvicorn 不影响 CLI、网页与测试。

### 四、验证

- 离线用例 617 → **636**（新增 19 个），全绿。
- 评测 **53/53**、64 次调用、90,542 输入 tokens，与 0.16.0 的 90,597 持平（模型波动）。
- 真实 HTTP 握手 `initialize → notifications/initialized → tools/list` 正常；
  带令牌服务实测无令牌 401、错令牌 401、伪造 Host 403、正确令牌 200。

### 五、同步清单

1. `python -m unittest discover -s tests` 应为 **636 passed**；`python -m app.cli version` 为 `0.17.0`。
2. 无新增必装依赖；`requirements-mcp.txt` 不变（uvicorn 随 mcp 安装）。

## 0.16.0 — 2026-11-26

**一句话**：SQL 写出来了、也能跑，但结构本身可能把数字算错。执行前加一层纯代码
结构审查：笛卡尔积拦下并让模型改写，`SELECT *` 与非唯一键关联只给提示。

### 一、用户能感受到的变化

- 模型若写出 `FROM orders o, customers c` 这类没有关联条件的多表查询，**不会执行**；
  系统把"会产生笛卡尔积、请改成 JOIN ... ON"回喂给它改写一次（状态机走通用重试环，
  线性引擎本地改写一次）。改写不出来就如实报错，**不会拿单表 pandas 做一个近似答案**。
- 结果里出现 `SELECT *`、两侧都不是唯一键的 JOIN、显式 `CROSS JOIN` 时，
  命令行多一行 `[结构审查提示：…]`，网页在结果上方给出同样提示。结果照常返回 ——
  这些写法**可能**是对的，误拦的代价更大。
- 缓存复用、`teach` 沉淀的 SQL 同样要过审查，没有旁路。
- `-f json`（以及 MCP 的 `ask`）新增 `review.blocked` / `review.issues`；
  网页侧栏和 `--no-review` / `AGENT_SQL_REVIEW=0` 可以关掉这一层。

### 二、判据为什么这样分

| 问题 | 处置 | 理由 |
| --- | --- | --- |
| 逗号连表无关联、JOIN 没有 `ON`、`ON 1=1` | 拦截 + 回喂改写 | 必然算错，且可能把 CPU 打满 |
| `SELECT *`、两侧都不唯一的 JOIN、`CROSS JOIN` | 只提示 | 可能是对的（如先 GROUP BY 的多对一），拦错比漏判更伤 |

唯一性**只认声明**：单列主键、单列 UNIQUE 索引、`catalog.yaml` 中被别的列 `ref`
指向的列、relationships 里标注"多对一 / 一对一"的右侧列。复合主键不算单列唯一；
拿不到信息就不报。"看起来像 ID"不是判据。

### 三、实现上的两个刻意选择

- **审查点放在 execute 之前**，而不是跟在生成节点后面：所有 SQL 入口（现写 / 缓存 / teach）
  在这里汇合，少一条绕过路径。被拦下的语句标记 `review_blocked`，让反思节点保持 SQL 路线。
- **不引 SQL 解析器**：先遮蔽字符串和注释，再按括号深度只取顶层子句 ——
  `'SELECT *'`、注释里的关键字、CTE 子查询、函数里的 `COUNT(*)` 都不会误报。
  新增 `tests/test_sql_review.py` 逐条跑评测集金标准 SQL，任何一条被报问题就红灯。

### 四、验证

- 离线用例 592 → **617**（新增 25 个），全绿。
- 评测 **53/53**、64 次调用、90,597 输入 tokens，与 0.15.0 的 90,557 持平（模型波动）。
- 金标准 SQL 零误报；被拦下的查询保持 SQL 路线、不换 pandas（两引擎各有回归用例）。

### 五、同步清单

1. `python -m unittest discover -s tests` 应为 **617 passed**；`python -m app.cli version` 为 `0.16.0`。
2. 无新增依赖；已有缓存与会话文件无需迁移（缓存 SQL 在执行前被审查，不会污染文件）。
3. `-f json` / MCP 只**新增** `review` 字段，旧字段含义不变。

## 0.15.0 — 2026-11-26

**一句话**：同一个问题问第二遍，不再让模型重写 SQL —— 命中历史查询时 **模型调用 0 次、
token 0**，耗时 3.31 秒 → 1.04 秒，结果与第一次完全一致。

### 一、用户能感受到的变化

- **重复提问近乎免费**：`ask "各区域的销售额是多少？"` 再问一次，输出多一行 `[复用]`，
  链路从 5 段缩到 3 段（`cache → execute → answer`），不再走计划与生成。
- **结果不会变**：复用的是上次**跑通过**的那条 SQL，执行的仍是当前库；只有当结果表
  与上次一字不差时，上次的结论才一并复用，数据变了就只复用查询、结论重新生成。
- **想强制重算**：`--no-cache`。调整口径、怀疑数字时用它对比一次。
- `-f json` 新增 `cache.hit` / `cache.note` 两个字段，脚本与 MCP 调用方能判断
  "这条 SQL 是模型现写的还是复用的"。

### 二、哪些情况绝不复用（每条都对应一种"复用就答错"）

- **多轮追问**：同一句话在不同上下文里指向的可能是不同的东西；
- **归因问题**：要的是"两期 × 维度"交叉表，对比期不在问题原文里；
- **问题里的取值库里没有**：该走澄清，不能让一条旧 SQL 把澄清盖掉；
- **时间完全超出覆盖**：该说明"没有数据"，不能拿旧 SQL 算个别的区间。

缓存键里带四样东西：问题（归一化）+ **库结构指纹** + **词典口径指纹** +
**相对时间的换算区间**。最后一项是关键：「上个月」的 SQL 里是显式日期，
绑"今天是哪天"会在同月内换天时白白失效，绑"换算出来的区间"两头都对
（1 月 15 日和 1 月 20 日都指 2025-12，可复用；2 月就不是了）。

### 三、几处刻意的设计

- **复用的 SQL 跑不通就作废，且不换 pandas 路线**。换路是"模型理解错"的处置，
  这里错的是缓存本身；换成 pandas 会绕开 JOIN 与聚合能力，得到的表也对不上。
- **只缓存真的给出答案的那一次**。空结果、拒答、澄清都不进缓存 —— 固化下来
  等于把"当时答不了"变成"永远答不了"，而数据是会变的。
- **`teach` / `lessons --rm` 清空当前库缓存**。不清会有个很隐蔽的坑：teach 之后
  问题原文没变，复用直接命中修正**之前**的语句，"教过了却还是错的答案"，日志里一切正常。
- **缓存文件本地可改，所以执行前再过一次安全检查**：一条被塞进来的 `DROP` 若照跑，
  复用就成了投毒通道。

### 四、验证

  同一批问题跑第二遍时命中缓存等于让上一轮答案给这一轮打分，冷启动口径必须每次都真跑。

## 0.14.0 — 2026-11-26

**一句话**：提示词里 schema 和术语原来被**每条 few-shot 示例各带一份**（占整份 prompt

### 二、改了什么

- `USER_TEMPLATE` / `SQL_USER_TEMPLATE` 不再包含 `{schema}` / `{terms}`，
  只剩「用户问题 + 输出要求」。
- `app/nodes/generate.py` 新增 `_system_with_context()`：把 schema 与术语拼进 **system 消息**，
  并在前面加一句「唯一权威来源，下面的示例里不再重复」。
- 为什么放 system 而不是"只在当前问题前放一份"：system + 示例是**跨问题不变的前缀**，
  DeepSeek 的上下文缓存只在相同前缀上命中；放在最后一条消息意味着每次都要重新计费。

### 三、为什么值得单独发一版

这类退化**改的人看不见**：把 `{schema}` 写回模板，功能完全正常、大部分用例照样全绿，

断言的是**出现次数**而不是"文本里有没有"：schema 出现 1 次、术语标题出现 1 次、
示例里一次都不许有、以及"新写法必须比老写法短 40% 以上"。

## 0.13.1 — 2026-11-26

**一句话**：补上「半年」这个时段的守卫 —— 以前问「上半年」时，把范围偷偷换成全年
是没人管的；顺带修掉「今年上半年」被当成「今年全年」注入提示词的错。

### 一、用户能感受到的变化

- 问句里出现 **上半年 / 下半年 / H1 / H2**（含「2025 年下半年」「2025H1」）时：
  - 首轮按半年回答；若首轮空结果触发重试，重试语句把半年换成**全年**、
    **某个季度**或**单月**都会被拦下，回答里直说"被换成了别的时段"，不再拿别的范围顶替。
  - 例如问「2025 年上半年的销售额」而库里上半年没数据时，以前会静默返回全年数字，
    现在会说这一半年确实没有数据。
- 「今年上半年」「去年下半年」「前年上半年」这类**带年份词的**半年，
  由系统换算成显式日期区间后随提示词下发（`2026-01-01 ~ 2026-06-30`）。
  以前这类说法会被「今年」抢先按**全年**注入 —— 比不认半年更糟，模型会照着答全年。
- 计划阶段也拦：如果生成的计划把半年写成全年（上半年 1-6 月却给了 1-12 月），
  直接判为致命并列明原因，不再白花一次生成调用。

### 二、行为和以前哪里不一样

- 只有带半年的问题受影响，其它问题一字未动（提示词没改）。
- 裸「上半年」（不带年份）**不猜年份**：它本来就是字面条件，交给范围守卫按
  "1-6 月"守，不在这里把用户的年份替成"今年"。

### 三、几个刻意这么定的地方

| 选择 | 为什么 |
| --- | --- |
| 不按"6 月/12 月在不在"判 | 半年区间常以「下半年首月 1 日」为上界（`< '2025-07-01'`），此时 6 月根本不出现，按月份判会把**正确**答案拦掉 |
| 7 月要按方向区分上/下界 | `< '2025-07-01'` 是"到 6 月底"（上半年），`>= '2025-07-01'` 是下半年起点 —— 同一个 7 月，指的半年相反 |
| 接受"只卡上界"的写法 | `WHERE strftime('%Y')='2025' AND strftime('%m') <= '06'` 是正确写法，但一月不出现。一开始按"1 月必须出现"判，正确写法被判成换范围 |
| 边界年份也要对 | `>= '2024-07-01'` 拿来答「2025 下半年」，边界在 2024，不能算"下半年还在" |
| 计划层只拦"放大" | 计划里把半年收窄成更短的区间，重试守卫那条链路管得着；计划层多拦一类只会增加误拒 |

### 四、怎么验证的

- 离线用例 526 → **545**：`tests/test_scope.py` 新增 12 个（正反例各半，含逐月展开 / 日期区间 /
  只卡上界 / 裸数字 / 上下半年互换 / 换到上一年，再加一条端到端「放宽成全年必须丢掉数据」）、
  `tests/test_time_anchor.py` 3 个、`tests/test_plan.py` 4 个。
- 半年锚点与归因的半年判定做了**对拍用例**（同季度那条），改一处忘另一处会红。
- 评测 53/53 不变（见 `evals/reports/baseline.md`）。

### 五、已知边界

- 只认公历自然半年（1-6 / 7-12）。财年制、自定义"上半年"（如 4-9 月）不认，
  这类口径请在 `catalog.yaml` 的指标说明里写清楚。
- 跨年区间的计划不做半年校验（边界写法太多），宁可漏判。
- `H1` / `H2` 是按英文缩写认的，问题里出现基因名之类的情况会被误认 —— 本项目场景下不会遇到。

- 新模块 `app/tools/catalog_gen.py`（纯函数）：`profile_schema`（实测画像）/

- **分工是这条功能的全部设计**：代码负责事实（类型、样例、枚举取值、主外键、行数），
  模型负责语义（中文名、说明、hints、口径建议），人负责拍板。反过来让模型看数据自己总结，

**一句话**：模型对某列的取值没把握时，可以先**只读地看一眼真实数据**再写 SQL ——
不用再靠猜"京东"到底存成 `京东` 还是 `JD`，也不再因为猜错而拿到一行 NULL 却看不出错。

### 一、用户能感受到的变化

- 当问题里点名了一个具体取值（渠道、状态、支付方式、客户名之类），而这一列不在术语口径里时，

  ```
  [探查] orders.channel → 4 个取值：Online / Offline / JD / Tmall
  ```

  网页端在结果区多一行小字。**它说明这个数是在看过真实取值之后算的**，而不是猜对的。
- 以前这类问题会给一个"看着正常"的空结果（`WHERE channel = '京东'` → NULL → "没有匹配数据"），
  现在会先用真实取值改写再算。
- 新增 `--no-peek`（命令行）与侧边栏开关（网页）：默认开启；关掉即回到 0.10.0 的行为。

### 二、行为差异（对已有用法的影响）

- **只在需要时才多一次调用**：探查由模型自己判断要不要，不是每道题都加一步。

- 探查**不会**产生答案：它只是把取值看一眼，任何探查结果都不会被当成查询结果返回。
- 探查失败（列名写错、语句越界）也不会让问答失败：原因会回灌给模型，让它改正后重写。

### 三、内部改动

- 新模块 `app/tools/peek.py`（纯函数 + 一个只读执行）：`parse_peek` / `strip_peek` /

- **白名单而不是黑名单**：只允许 `SELECT [DISTINCT] 列, ... FROM 一张表 [WHERE/ORDER BY/LIMIT]`，

- **额度 1 次/问答**：额度按整次问答算（进 state），重试不再探；用完仍会重新生成一次并明说；
  第二次仍要探查就把那行剥掉 —— 不会把 `PEEK:` 当 SQL 去执行。

## 0.10.0 — 2026-11-25

**一句话**：复杂问题在写 SQL 之前，先让模型交一份**结构化查询计划**（指标 / 表 / 维度 / 过滤 / 时间 / 假设），

### 二、行为差异（对已有用法的影响）

- **成本**：43 条有答案评测题中 10 条触发计划，token 约 +22%（137,570 → 168,292），
