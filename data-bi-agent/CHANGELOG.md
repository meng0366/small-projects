# 变更说明

面向协作方的同步文档：这次改了什么、行为和以前哪里不一样、需要做什么。
按版本倒序排列。版本号与 `python -m app.cli version` 一致。

## 0.13.0 — 2026-11-26

**一句话**：这个 Agent 现在可以被别的 Agent 直接调用了 —— `python -m app.cli serve`
把它变成一个 MCP server，`ask` / `get_schema` / `generate_catalog` 三个工具对外。

### 一、用户能感受到的变化

- 装可选依赖、启动：

  ```bash
  pip install -r requirements-mcp.txt        # 在 requirements.txt 之上加一个 mcp
  python -m app.cli serve                    # stdio，默认用 data/sales.db
  python -m app.cli serve --db 我的库.db      # 换默认库
  ```

  在 Claude Desktop 的 `claude_desktop_config.json` 里配：

  ```json
  {
    "mcpServers": {
      "data-bi-agent": {
        "command": "D:/path/.venv/Scripts/python.exe",
        "args": ["-m", "app.cli", "serve", "--db", "D:/path/data/sales.db"],
        "cwd": "D:/path/data-bi-agent"
      }
    }
  }
  ```

- 三个工具：

  | 工具 | 干什么 | 对应命令 |
  | --- | --- | --- |
  | `ask` | 中文提问，返回数据 + 生成的 SQL + 执行信息 | `ask -f json` |
  | `get_schema` | 表/列（含中文名）、指标口径、表关系 | `schema --json` |
  | `generate_catalog` | 给陌生的库生成词典草稿（会写文件） | `catalog` |

- 返回的是 JSON，与 `ask -f json` **同一份结构**（同一份代码），所以脚本里怎么读，
  这里就怎么读。数据默认只给前 200 行，并写明 `truncated` 与真实的 `rows`。

### 二、行为和以前哪里不一样

- **没有变化**：命令行、网页、评测口径全都不动。53 条评测仍是 53/53、63 次调用、
  token 持平（179,065），因为这一版没碰任何提示词。
- 唯一的内部调整：`-f json` 的 payload 构造从 `app/cli.py` 挪到 `app/payload.py`，
  让 MCP 工具与命令行读同一份 —— 否则两边字段名各自演化，第一个踩坑的是读 JSON 的脚本。

### 三、几个刻意这么定的地方

| 选择 | 为什么 |
| --- | --- |
| stdio 下一行 print 都没有 | stdout 是 JSON-RPC 通道，混一行提示客户端就连不上。CLI 那套带 print 的 `run_*` 一个都不复用，只复用不打印的那层 |
| 数据截断到 200 行且标注 | 返回值进的是另一个模型的上下文窗口。悄悄只给一部分，比截断本身危险 |
| 错误返回 `{"ok": false, "error": ...}` 而不抛异常 | 对面看到 traceback 只会说"工具坏了"，看到结构化错误才会换问法或去告诉用户 |
| `insight` / `chart` 默认关 | 一个多花 token，一个写图片文件——MCP 场景下调用方要的是数字 |
| mcp 放可选依赖 | 它拖着 cryptography、pywin32 一串东西；只用命令行或网页的人不必装 |
| 没装 mcp 时测试 skip 而不是 fail | clone 下来默认环境应当全绿；CI 里装了 mcp，所以注册层在 CI 被真的测到 |

### 四、怎么验证的

- 离线用例 493 → **526**（新增 `tests/test_mcp_server.py` 33 个）。
- 未装 mcp 的环境：33 个用例里 5 个 skip（需要协议层的那些）、28 个照跑，全绿。
  这是"clone 下来不装可选依赖也能跑测试"的保证。
- 真实 stdio 握手（起子进程走 JSON-RPC）：
  ```
  initialize -> capabilities / instructions 正常返回
  tools/list -> ['ask', 'get_schema', 'generate_catalog']
  get_schema -> 返回 3 张表的结构
  ask("各区域的销售额是多少？", max_rows=3)
      -> ok=true · route=sql · rows=5 · truncated=true · data 长度 3
      -> trace_id 20261126-002002-900001
  stderr 空、退出码 0
  ```
- 评测 53/53 不变。

### 五、已知边界

- **只支持 stdio**。HTTP 传输（streamable-http）要按客户端的部署方式配，
  各版本 mcp SDK 的启动参数还不统一，这一版不做，避免写一段"本地跑得通、
  换台机器就不行"的代码。
- 一次 `ask` 就是一次完整问答（含计划/探查/重试），**耗时 2 秒起**，
  客户端要有耐心；它不适合"一次问 50 个问题"的批处理场景，那种场景请用命令行。
- 没有鉴权概念：stdio 是本地进程，谁起进程谁就是这个用户。别把它包到公网端口上。

## 0.12.0 — 2026-11-26

**一句话**：接一个新库不用再手抄 `catalog.yaml` —— 一条命令把表结构、样例值、枚举取值、
主外键**实测**出来，再让模型补上中文名、说明与指标口径，落成一份带 TODO 的草稿等人确认。

### 一、用户能感受到的变化

- 新增命令：

  ```
  python -m app.cli catalog --db 我的库.db            # 生成 catalog.draft.yaml
  python -m app.cli catalog --db 我的库.db --dry-run   # 只看能自动认出什么（零成本、不调模型）
  python -m app.cli catalog --db 我的库.db --merge app/schema/catalog.yaml   # 只补空缺
  ```

  终端先报自动识别到的规模，再报草稿写在哪：

  ```
  自动识别：3 张表 · 17 列 · 4 个枚举列 · 2 条表关系
  草稿已写入：catalog.draft.yaml
  表 3 张 · 列 17 个 · 指标口径 6 条
  ```

- 生成的草稿长这样（给示例库加了一列 `channel` 的临时库）：

  ```yaml
      channel:
        label: 销售渠道
        type: string
        example: Online
        values: [JD, Offline, Online, Tmall]
        hints: [渠道, 销售渠道, 下单渠道]
  ```

- 新增 `AGENT_CATALOG` 环境变量：不覆盖内置词典，也能让整条链路用你的草稿。

### 二、行为差异（对已有用法的影响）

- **对问答零影响**：`catalog` 是离线命令，不改任何提示词、不增加调用。
  53 条评测仍是 53/53、63 次调用、token 与 0.11.0 持平。
- 默认只写草稿，**绝不覆盖 `app/schema/catalog.yaml`**；`--merge` 也只补空，
  已有的非空字段（中文名、说明、口径）一个字都不动。
- 草稿默认落在当前目录 `catalog.draft.yaml`，已加进 `.gitignore`（确认后应改名/覆盖到词典）。

### 三、内部改动

- 新模块 `app/tools/catalog_gen.py`（纯函数）：`profile_schema`（实测画像）/
  `format_profile` / `map_type` / `is_enum_candidate` / `build_draft`（三方合并）/
  `validate_draft` / `render_catalog_yaml` / `count_todos`。
- **分工是这条功能的全部设计**：代码负责事实（类型、样例、枚举取值、主外键、行数），
  模型负责语义（中文名、说明、hints、口径建议），人负责拍板。反过来让模型看数据自己总结，
  它会凭常识补一个库里没有的"华东区"—— 词典是要拿去约束生成 SQL 的，编造的取值比没有更糟。
- **枚举识别四条判据**：非主键、去重 2~20、去重 < 行数×0.8（挡"每行都不同"的标识符）、
  文本列直接算候选而数值列只在列名像状态/类型/等级时才算（挡 `quantity` 1~5）。
  另加标识符命名排除（`_id` / `_no` / `_code`）—— 这是实测时抓到的真 bug：
  `orders.customer_id` 在 3877 行里 20 个不同值，按"去重少 + 文本"会被认成枚举，
  然后 schema 里就会写出「customer_id 必须严格使用以下字面量：C001 / C002 / ...」。
- **外键推断三条必须同时成立**：同名列 + 目标列唯一 + 源值域是目标子集。少了值域校验，
  `order_id` 与 `customer_id` 会互相认成外键。表数 > 40 时跳过推断，只保留建表声明的。
- **渲染必须能被 `yaml.safe_load` 原样读回**：日期样字符串（`2025-01-05`）、数字样字符串（`001`）、
  布尔样（`true`）、含 `: # [ ] ,` 的值一律加引号 —— 否则重新加载会变成 date / int / bool。
  这条有专门的往返回归用例兜着。
- **hints 是必须产出的**：`enum_guard` 靠 hints 定位"他是在说哪一列的取值"。
  不产 hints 的话，新库的枚举列虽然有取值也拦不住错值，这条防线对新库等于不存在。
- 模型返回的表列逐条核对：不存在的表/列**丢掉**（不能让幽灵列进词典），
  漏掉的列保留实测事实并标 TODO；口径的 `source` 必须能指到真实列，否则丢弃。

### 四、验证

- 离线用例 445 → **493**（新增 `tests/test_catalog_gen.py` 48 个：类型映射、枚举四条判据、
  外键声明与推断、脏 JSON 解析、表列核对、三方合并优先级、YAML 往返与特殊字符转义、
  草稿喂给 `build_db_schema_text`、草稿激活 `enum_guard`）。
- 评测 **53/53（100%）** 不变；调用 63 次、token 179,066（零回归）。
- **真实对比**（临时库给 `orders` 加 `channel` 列：Online / Offline / JD / Tmall，
  问「只看京东渠道的销售额是多少？」）：

  | 配置 | 结果 |
  | --- | --- |
  | 自动生成的词典 | 1 次调用，直接澄清：「你提到的「京东」不在库里的销售渠道取值中。现有可选值：JD / Offline / Online / Tmall」，**未生成 SQL** |
  | 内置词典（不认识 channel） | 生成 `WHERE channel = '京东'` → 一行 NULL → "当前条件下没有匹配到数据" |

  第一行正是这条功能的价值：**把"要靠探查才救得回来"的情况，变成"生成前就澄清"**，
  而且还更省（1 次调用 vs 3 次）。

### 五、已知边界

- 只支持 SQLite（与项目其它部分一致）。不含指标口径的**业务含义**（毛利率、转化率这类
  必须人工定义，模型不该猜）。
- 列的中文名靠模型提议，**可能与你同事的说法不一致**（模型给"销售金额"，大家问"销售额"）。
  草稿注释里写明了这点：口径名必须自己过一眼。
- 枚举识别会漏认（小表上"去重 / 行数"天然接近 1、`status_code` 这类被标识符规则排掉）。
  漏认的后果是少一层取值约束，不会答错，这种列仍可被两段式探查兜住。
- 表结构过大（画像超 24000 字符）会拒绝而不是截断 —— 硬截断会让模型交出半份词典。

## 0.11.0 — 2026-11-25

**一句话**：模型对某列的取值没把握时，可以先**只读地看一眼真实数据**再写 SQL ——
不用再靠猜"京东"到底存成 `京东` 还是 `JD`，也不再因为猜错而拿到一行 NULL 却看不出错。

### 一、用户能感受到的变化

- 当问题里点名了一个具体取值（渠道、状态、支付方式、客户名之类），而这一列不在术语口径里时，
  命令行会多出一行：

  ```
  [探查] orders.channel → 4 个取值：Online / Offline / JD / Tmall
  ```

  网页端在结果区多一行小字。**它说明这个数是在看过真实取值之后算的**，而不是猜对的。
- 以前这类问题会给一个"看着正常"的空结果（`WHERE channel = '京东'` → NULL → "没有匹配数据"），
  现在会先用真实取值改写再算。
- 新增 `--no-peek`（命令行）与侧边栏开关（网页）：默认开启；关掉即回到 0.10.0 的行为。

### 二、行为差异（对已有用法的影响）

- **只在需要时才多一次调用**：探查由模型自己判断要不要，不是每道题都加一步。
  自带示例库的 53 条评测里 **0 次触发**（区域/品类/客户等级都写在 `catalog.yaml` 里，
  模型有取值可依），调用次数不变。
- **token 略增 6.4%**（168,292 → 179,084）：这是提示词里新增一条规则带来的固定开销，
  与是否真的探查无关。在意成本可用 `--no-peek`（它会让这条规则不生效）。
- 探查**不会**产生答案：它只是把取值看一眼，任何探查结果都不会被当成查询结果返回。
- 探查失败（列名写错、语句越界）也不会让问答失败：原因会回灌给模型，让它改正后重写。

### 三、内部改动

- 新模块 `app/tools/peek.py`（纯函数 + 一个只读执行）：`parse_peek` / `strip_peek` /
  `check_peek_sql`（白名单）/ `run_peek` / `format_peek_result` / `summarize_peek` / `maybe_peek`。
- **白名单而不是黑名单**：只允许 `SELECT [DISTINCT] 列, ... FROM 一张表 [WHERE/ORDER BY/LIMIT]`，
  禁 JOIN / UNION / 子查询 / WITH / 聚合函数 / `*`，纯列名、最多 4 列；执行最多 50 行、
  每列最多回灌 30 个取值、单值 30 字符。原因：探查是"看一眼取值"，不是"跑个查询"，
  收窄到能被用户一眼看懂的形态，才不会把整库扫描能力开放给一次顺手的调用。
- **额度 1 次/问答**：额度按整次问答算（进 state），重试不再探；用完仍会重新生成一次并明说；
  第二次仍要探查就把那行剥掉 —— 不会把 `PEEK:` 当 SQL 去执行。
- **两引擎共用 `maybe_peek`**：状态机的 generate 节点与线性 `_try_sql` 都传各自的生成函数进去，
  流程只有一份实现（P2-2 的教训：不能只有状态机支持）。
- 追踪：`generate` 事件多 `peek / peek_rows / peek_ms`，汇总行同上，`-f json` 多 `peek` 对象。
  仍只记标量 —— 探查到的取值不落盘。
- 提示词 `SYSTEM_SQL` 新增第 12 条，并明确它是"只输出一条 SELECT"的唯一例外。

### 四、验证

- 离线用例 390 → **445**（新增 `tests/test_peek.py` 55 个：解析、白名单 16 条正反例、
  回灌格式、额度与死循环、两引擎端到端）。
- 评测 **53/53（100%）** 不变，执行成功率 43/43，拒答/澄清 10/10。
- 真实试跑（临时库给 `orders` 加一列 `channel`，取值 `Online / Offline / JD / Tmall`）：
  1. `只看京东渠道的销售额是多少？`
     - 开探查：`[探查] orders.channel → 4 个取值：Online / Offline / JD / Tmall`，
       SQL 用 `WHERE channel = 'JD'`，答 **4,563,724.05**（与该渠道分组合计一致）；
       链路 `generate 1237ms · peek=True · peek_rows=4 · peek_ms=627`。
     - `--no-peek`：`WHERE channel = '京东'` → 一行 NULL → "当前条件下没有匹配到数据"。
  2. `各渠道的销售额是多少？` → 不需要具体取值，模型直接 `GROUP BY channel`，**不探查**（判定正确）。

### 五、已知边界

- 示例库上探查基本不触发（枚举列都在 `catalog.yaml` 里）—— 这条能力的收益要到接自己的库时才有。
  想试：给库加一个有枚举但不在词典里的列，然后问"只看 XXX 的……"。
- 探查只覆盖 SQL 路线；pandas 路线没有库可查。
- 是否探查由模型判断，规则式判据只能写在提示词里，**偶尔会漏判**（漏判=少一次校验，不会答错）。
- 只允许"点名列"的简单形态：想看"有哪些年份"只能 `SELECT DISTINCT order_date`，
  用 `strftime` 会被拒（错误信息会说明原因）。

## 0.10.0 — 2026-11-25

**一句话**：复杂问题在写 SQL 之前，先让模型交一份**结构化查询计划**（指标 / 表 / 维度 / 过滤 / 时间 / 假设），
由代码核对"时间有没有数据、取值是否真实、年份有没有被换掉"，通过才允许生成 SQL。

### 一、用户能感受到的变化

- 复杂问题（比率/派生指标、多层限定、多轮追问、归因）会多一步"思考"，命令行多出一段：

  ```
  [计划] SUM(amount) · 按 region 分组 · 2 张表
    · 假设：客单价按 SUM(amount) / COUNT(order_id) 计算，按 region 分组
  ```

  网页端在结果上方多一个「查询计划」折叠区，默认收起。
- 有些以前会给数的问题，现在会先说明原因：计划里出现的取值库里没有、时间区间没有数据、
  年份与提问不一致 —— 三类都在生成 SQL 之前拦下，不浪费一次生成的调用。
- 新增 `--no-plan`（命令行）与侧边栏开关（网页）：默认开启；关掉即回到 0.9.2 的调用量。

### 二、行为差异（对已有用法的影响）

- **成本**：43 条有答案评测题中 10 条触发计划，token 约 +22%（137,570 → 168,292），
  调用 46 → 63 次。准确率不变（53/53）。不想承担这部分成本就 `--no-plan`。
- **简单问题完全不受影响**：短、单维度、无过滤的问题（如"各区域的销售额是多少？"）
  一次计划调用都不会有。判定是零 token 的规则，不是再问一次模型。
- **多轮追问也走计划**：省略说法（"只看华东"）容易改错对象，值得先对齐一次。
- 计划里的假设（"用户说 6 月，按 2025 年 6 月计算"）会展示出来，与归因的 `assumed` 同一原则：
  替用户做的决定必须写出来。

### 三、内部改动

- 新模块 `app/tools/plan_guard.py`（纯函数）：`needs_plan` 判定、`parse_plan` 容错解析、
  `validate_plan` 校验、`format_plan_hint` 拼提示。
- 新节点 `app/nodes/plan.py`：状态机在 `understand → generate` 之间插入 `plan`；
  线性编排走同一个 `build_plan`，两个引擎不会有两套口径。
- 三类致命问题**接到已有的短路机制**上，不新造终止节点：
  时间无交集 → `time_defer`；取值不存在 → `unknown_enum`（复用澄清）；
  年份/月份被换 → `defer`。`clarify` 节点现在也处理 `defer`。
- 表名列名对不上只算提醒（拼进生成提示），不阻断 —— 带前缀/别名的情况太多，误拦比漏拦更伤。
- 计划解析失败 → 退回普通生成：计划是增强，不能成为单点故障。
- 重试时沿用同一份计划（空结果重试不许改口径，计划正是那条口径）。
- 追踪链里多一个 `plan` 阶段，汇总行多 `plan` / `plan_issues` 字段。
- 归因问题跳过"年份/月份一致性"校验：它比的是两期，计划的 `time_range` 只有一个区间，按单期校验会误拦。

### 四、验证

- 离线用例 352 → **390**（新增 `tests/test_plan.py` 38 个：判定、解析、三类拦截、两个引擎端到端）。

### 二、行为变化（可能和以前的输出不一样）

- **时段被建模成"跨度"**：单月 `(2025,6,6)`、季度 `(2025,4,6)`、半年 `(2025,1,6)`、自定义区间 `(2025,3,5)`。
  由此带来三条可观察的差异：
  1. 用户说 `Q1`、数据里是 `2025-01` 这样的月份行时，现在能对上（按"有交集"匹配）；以前对不上。
  2. "只说一期"时，默认比较的是**同长度的前一段**（Q2 → Q1、上半年 → 去年下半年），
     而不是简单减一个月（以前会拿 Q2 去和 5 月比）。
  3. **单期且前一段跨年时不做归因**：如「为什么 3-5 月销售额下降了」，前一段是去年 12 月–今年 2 月，
     当前的时段表示法写不出跨年区间，于是老实退回普通查询，不拼一个起止颠倒的假区间。
- **「从 5 月到 6 月」仍按方向读**（5 月 → 6 月），不当作一个 5-6 月的区间。
  只有不带「从」的写法（`3-5 月`、`3 月到 5 月`）才当区间。
- **`logs` 表新增 `engine` 列**（`graph` / `linear`）。线性路线不挂 token 回调，
  该列显示 `—` 而不是 `0/0` —— 宁可说"未统计"，也不假装统计过。
- **范围守卫多认一种锚点**：`3-5 月` 这类区间整体作为一个"不许换掉"的条件；
  区间内的月份不再单独当锚点。逐月展开、以及"上界写成下一个月 1 日"的日期区间写法都放行，
  只有被缩窄（如 3-5 月只查 2025-05）时才拦。
